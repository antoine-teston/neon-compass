# Run de veille — 2026-08-20

## Arrêt à l'étape 1 : conflit de fusion en resynchronisant `veille/courante` avec `main`

```sh
git checkout -B veille/courante origin/veille/courante
git merge origin/main --no-edit
```

a produit un conflit `both added` sur quatre fichiers :

- `content/news/news_5039f9ad.json`
- `content/news/news_807a16dc.json`
- `content/news/news_9d991161.json`
- `content/news/news_a907cde2.json`

Le contrat est explicite (§1) : « Si la fusion entre en conflit : arrête-toi,
rapporte le conflit dans un compte-rendu de run, et ne force rien. » J'ai donc
fait `git merge --abort` et n'ai exécuté aucune autre étape de la chaîne
(pas de déclenchement de `recolte.yml`, aucune extraction, aucune
matérialisation) : sans une branche roulante saine, tout le reste tournerait
sur une base que je ne peux pas garantir à jour.

### Ce que dit le diff

Sur les quatre fichiers, le conflit est identique : mêmes textes dans les
cinq langues des deux côtés, mais

- côté `veille/courante` (HEAD) : `"status": "draft"`, pas de `listedAt` ;
- côté `origin/main` : `"status": "published"`, `"listedAt": "2026-08-19"`.

Ce sont exactement les quatre actus rédigées lors du run du 2026-08-19 (voir
`content/inbox/runs/2026-08-19.md`, section « Faits extraits ») — la fuite de
gameplay, le mémo militaire, le recadrage 60 fps, et la publicité console
sans image inédite. Elles ont été ouvertes en PR puis fusionnées sur `main`
via « Fusion de la veille », et quelque chose en aval sur `main` (probablement
`publish-news`, mentionné au §Règles dures du contrat) leur a depuis ajouté
`listedAt` et fait passer `status` à `published`. La branche `veille/courante`,
elle, n'a pas bougé depuis la fusion de cette PR : elle porte donc toujours la
version `draft` d'origine des mêmes quatre fichiers, sans ancêtre commun que
git puisse reconnaître pour ces fichiers précis — d'où le `both added` plutôt
qu'un conflit de modification ordinaire.

Autrement dit : ce n'est vraisemblablement pas deux runs qui se contredisent,
mais une branche roulante qui a pris du retard sur une transformation faite
en aval sur `main` après sa propre fusion. Je ne le corrige pas moi-même —
le contrat est explicite sur ce point aussi : « Une branche roulante qu'on ne
sait plus resynchroniser se supprime à la main après relecture — ce n'est pas
ta décision. » Une option qu'un humain voudra peut-être évaluer : supprimer
`veille/courante` et la recréer depuis `main` (qui semble déjà porter tout ce
que la branche roulante contenait, publié), plutôt que de résoudre le
conflit fichier par fichier. Mais ce choix ne m'appartient pas.

## Résolution — 2026-08-20, côté humain (hors Routine)

Le conflit est résolu **fichier par fichier**, et non en supprimant la branche
roulante. Le diagnostic ci-dessus est exact et a été revérifié : sur les quatre
fichiers, les deux versions sont identiques à deux lignes près, et `main` est
strictement en avance (`"status": "published"` + `"listedAt": "2026-08-19"`
contre `"status": "draft"`). La version de `veille/courante` est donc l'ancêtre
périmé : les quatre conflits prennent la version de `main`, sans exception.

Pourquoi pas supprimer/recréer, l'autre option envisagée. Vérification faite
fichier par fichier, `main` porte déjà presque tout ce que la branche roulante
contenait — `content/inbox/2026-08-19-gta6-veille.facts.json` et
`content/inbox/runs/2026-08-19.md` y sont. **Un seul fichier n'existe que
sur la branche : ce compte-rendu-ci.** L'option supprimer/recréer était donc
moins coûteuse que ne le laissait croire le doute exprimé plus haut, mais elle
effacerait la trace du run qui a signalé le problème — et résoudre ne coûte
que quatre `checkout --theirs`.

Après cette fusion, le diff de la PR se réduit à ce seul fichier, sous
`content/inbox/` — soit le périmètre que « Fusion de la veille » accepte.

**La journée du 2026-08-20 reste non récoltée**, comme le note le run. Sans
conséquence : `recolte.yml` est lancé avec `since=2`, donc le run du 2026-08-21
couvrira les deux jours.
